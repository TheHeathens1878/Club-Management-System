# P3.2 — auth mapping plan (NextAuth credentials → Supabase Auth)

Based on MIGRATION_MAP §2: the legacy app authenticates with NextAuth's
Credentials provider against local password hashes (bcrypt expected).

## Strategy A — import the hashes (preferred; no forced reset)

Supabase Auth stores bcrypt hashes in `auth.users.encrypted_password` and
accepts an existing **bcrypt** hash through the Admin API:

```ts
await admin.auth.admin.createUser({
  email,
  email_confirm: true,
  password_hash: legacy.passwordHash,   // "$2a$10$…" / "$2b$10$…"
  user_metadata: { full_name, person_id },  // person_id → P1.7 invite flow adopts the person
});
```

Conditions: the hash must be bcrypt (argon2/scrypt are not importable → use
Strategy B for those users); `user_metadata.person_id` points at the `people`
row P3.3 created, so `handle_new_user()` adopts it **only if** that person has
no profile yet and — for a minor — an active `app_account` consent (SG-10). All
imported users have unknown DOB, so `is_minor()` is true for every one of
them and the SG-10 `profiles` guard would refuse the profile. Two options for
Adam:

1. **Import DOBs first** (if the Neon data has them — §5 of the map) and mark
   adults as adults before creating auth users; or
2. **Create auth users without `person_id`** (a fresh person per login, as
   P1.2 does for any new signup) and let admins link/merge later — profile
   creation then passes because `handle_new_user()` creates a *new* person with
   NULL dob and the SG-10 guard only fires for a person who *already* exists
   as a known minor… **no:** a NULL-dob person is a minor under SG-0, and the
   guard refuses a profile for a minor without consent. So option 2 needs the
   **unknown-DOB carve-out** P1.7 records as awaiting Adam's agreement — the
   same carve-out every adult self-signup already relies on.

The dry run on a branch DB (P3.2 acceptance) will surface exactly how many
imports the SG-10 guard refuses under each option.

## Strategy B — password reset for everyone (fallback)

Create users with `email_confirm: true` and **no** password, then send the
comms email below with a "set your password" link
(`admin.auth.admin.generateLink({ type: 'recovery' })`). Sends go through
`enqueue_message('email', 'transactional', …)` so they are logged and respect
suppressions.
