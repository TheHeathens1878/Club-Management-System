## What it does

A `profiles` row — an app account — may exist for a **known** minor only while
that minor is an *account-eligible minor* (SG-0.1). The consent that makes that
true is recorded per child and per purpose, granted by an adult holding an
**active guardianship** to the child, revocable, never deleted, and every grant
and revocation audit-logged. The two age thresholds live in the existing
`public.site_settings` key/value table and are validated in the database rather
than in a settings screen.

### What is deliberately *not* changed

- **The two baseline `site_settings` policies** ("Anyone can read site_settings",
  "Committee can manage site_settings"), names and spaces included. Both
  safeguarding values are non-secret integers — an age threshold the club prints
  on its own consent form — so the world-readable SELECT is correct for them as
  it stands, and narrowing it would be a change to the imported app.
- **The imported function-room app.** Every trigger added to `site_settings` is
  scoped to keys matching `safeguarding.%`, and none of the 27 keys
  `apps/web/src/lib/settings.ts` knows about matches it. Asserted by test 61.
- **`guardianships_guard()`** is not refactored — see "Duplication over
  refactoring" below.
- **`is_committee()` / `is_staff()` / `is_bar_manager()`**, and every existing
  policy on every existing table. P1.7 adds one table and touches no other
  table's RLS.

## Decisions

### `granted_by` must be the guardian or a `club_admin`

SG-10's RLS sentence gives the grant to the guardian: "a guardian may read,
grant and revoke consents for their own children". §13 implements exactly that
for `authenticated` — there is **no admin INSERT policy**.

But consent is overwhelmingly given on paper at registration, and the person
typing it in is a club administrator working through `service_role`. Refusing
that would either push the club into logging in as the parent — destroying the
attribution the row exists for — or leave `granted_by` empty on most real rows.
So §9a's fourth check reads: **when `granted_by` is not null, it must resolve to
the guardian named on the row, or to a `club_admin`.**

`safeguarding_lead` is **not** admitted as a grantor. SG-10 gives the lead "read
all and may revoke", and P1.4 drew the same line on `person_roles`: the role
whose purpose is oversight must not be able to manufacture the permission it
oversees. Tests 99–102.

A **null `granted_by` is permitted**, for the Phase 3 legacy import and for any
migration-authored row — the position `person_roles.granted_by` and
`guardianships.created_by` already take. Attributing an imported consent to
whichever login happened to run the import would be a small lie in the record
that matters most.

### `safeguarding_lead` may revoke, alongside `club_admin`

SG-10: "`club_admin` and `safeguarding_lead` read all **and may revoke**." The
sentence names both roles and attaches both verbs to them, and SAFEGUARDING.md
§1 makes the document outrank a task description — the same precedent P1.4
followed when SG-4 gave both admin roles write on `guardianships`. It is also
right on the merits: a Club Welfare Officer who learns that an
unsupervised-messaging consent should not stand must be able to withdraw it that
minute, without finding a committee member first. Tests 160, 161.

### `has_active_consent()` does not re-check the guardianship

It checks three things: a row exists, it is not revoked, it has not expired. It
deliberately does **not** re-check that the granting guardian still holds an
active guardianship.

That is a **grant-time** condition (§9a), exactly as SG-4's age rules are
creation-time conditions ("the age tests apply at creation only"). Re-checking it
at read time would mean that ending a guardianship — a routine administrative
act — silently invalidated a child's app account with nothing happening in
`guardian_consents` at all. SG-10 is emphatic about the opposite direction:
"Revoking `app_account` consent does not delete the account… a trigger that did
it as a side effect of a consent edit would be a worse outcome than the gap it
closes." A guardian who no longer wants the consent to stand revokes it: one
column, one audit row, one visible act.

### A consent row is evidence: identity columns are immutable, and a revocation cannot be undone

§9b refuses, **for every role including the owner**, any change to
`child_person_id`, `guardian_person_id`, `consent_type`, `granted_at`,
`granted_by` or `notice_version`, and any change to `revoked_at` once it is set.

Retargeting a consent from one child to another, or quietly changing which
notice the guardian was shown, is not a correction — it is a rewrite of the
record a safeguarding enquiry would rely on. A consent entered against the wrong
child is revoked and re-granted, which leaves both facts visible. This is the
`guardian_consents` analogue of SG-1.8's refusal to let a guardianship be
retargeted silently, and SG-10's own test list already assumes it:
`consent_after_revocation_can_be_granted_again` is a **new row**, which the
partial unique index permits precisely because the old one is revoked.

**A non-admin may change only `revoked_at` / `revoked_by`.** "Admin" resolves
through `has_any_role()`, which resolves `current_person_id()`, which is NULL for
`service_role` and for the owner — so a caller with no JWT is treated as a
non-admin and may only revoke. Deliberate and fail-closed: an Edge Function has
no legitimate reason to rewrite a consent's notes, and if one ever does it will
do it through a named accessor with its own audit row, on the SG-3/SG-9 pattern.
Tests 103–107.

### The `profiles` guard also watches `UPDATE OF person_id`

SG-10 names only `BEFORE INSERT ON public.profiles`. A profile whose `person_id`
is repointed at a known ineligible minor reaches exactly the state the INSERT arm
exists to prevent, with nothing happening in `people` or `guardian_consents` —
the SG-1.8 shape of hole, and the same remedy. It is a reachable path:
`profiles_person_link.test.sql` itself updates `person_id`.

A **strengthening** under §6.2, recorded in DECISIONS.md. Test 131.

### Trigger firing order on `profiles` is load-bearing

Postgres fires `BEFORE ROW` triggers in **name order**. P1.2's
`trg_profiles_ensure_person` is what supplies `person_id` on an upsert that
arrives without one, so the SG-10 guard must run *after* it — otherwise it sees
a NULL `person_id` and waves the insert through.

`trg_profiles_ensure_person` < `trg_profiles_sg10_account_eligibility` under any
collation: the comparison is decided at the first character of the suffix
(`e` < `s`) and no punctuation is involved. Asserted, not assumed (test 27).

### Three guards became `SECURITY DEFINER`, and one of them was P1.1's

`guardian_consents_grant_guard()`, `profiles_account_eligibility_guard()` and
`people_dob_guard()` all read tables whose RLS is scoped.

P1.3's `guardianships_guard()` did not need this: a guardianship is written by an
administrator who can read all of `public.people` and all of
`public.guardianships`. A consent is written by a **parent**, whose reads of both
tables are scoped by RLS. A guard running as the caller could therefore fail to
*find* the very link it is checking for and raise "holds no active guardianship"
at a guardian who does — and the reverse shape of that mistake is a check that
**silently passes**.

`people_dob_guard()` is the sharpest case. Its new block asks "does this person
hold an account?" by reading `public.profiles`, whose policy is
`id = auth.uid() or is_committee()`. A `club_admin` who is not also
`profiles.role = 'committee'` — a person P1.4 makes possible and P1.6 makes
ordinary — would see only their own profile, the `EXISTS` would answer false, and
the SG-10 re-check would be skipped **without a word**. A silently-skipped
safeguarding check is the worst available outcome.

Consequence: §14 revokes the platform's default `EXECUTE` grants on
`people_dob_guard()` from all three API roles (test 47). A definer function
nobody needs to call is one nobody should be able to call.

### Duplication over refactoring for the adult-with-known-dob test

§9a re-implements the two checks inside `public.guardianships_guard()` — guardian
dob known, guardian is an adult — rather than calling a shared function.
Factoring them out would mean rewriting a P1.3 function whose exact `P0001`
message text `guardianships.test.sql` asserts. The duplication is four lines; the
alternative is a change to a tested safeguarding trigger in a migration that has
no other reason to touch it. If a third caller appears (P2.2 is the candidate),
factor it then, in a migration whose subject it is.

### `expires_at` ships present, honoured, and always NULL

SG-10: "left null until **D12** is settled; `has_active_consent()` treats a past
`expires_at` as inactive from the day it exists, so settling D12 later is a data
change rather than a schema change." Nothing in this migration writes it; §8b
honours it from the outset, and test 72 proves an expired consent is inactive
even with `revoked_at IS NULL`.

### Every `safeguarding.%` key must be an integer, not only the two age keys

That is what SG-10 says ("A `BEFORE INSERT OR UPDATE` trigger on `site_settings`
for keys beginning `safeguarding.` requires: the value to be an integer"), and it
fails in the safe direction. A future non-integer safeguarding setting is refused
loudly at the first write, which sends its author to
`site_settings_safeguarding_guard()` to decide deliberately how it should be
validated — rather than letting an unvalidated safeguarding setting into the
table unnoticed. Test 60.

### `settings.changed` fires on UPDATE only

Three consequences, all deliberate:

- The §7 seed writes no audit row. The migration is the record of the seed, and
  two rows attributed to nobody at the same instant is the noise P1.4's backfill
  went to some trouble to avoid.
- An UPDATE that rewrites the same value writes nothing — apps/web's settings
  screens upsert every key in a section on every save, so logging no-ops would
  fill the table with non-events (test 64).
- A DELETE writes nothing because §6b makes it unreachable.

`old` and `new` are rendered as JSON **numbers**, as SG-7's example shows.

### Deletion of a safeguarding key is refused

§5 fails closed to 13/14 if a row vanishes, so a deletion is not a hole in the
rule. It is still refused, because a deleted row and a row set back to its
default are indistinguishable to §5 but say very different things about what the
club decided — and because these two keys are read by SG-0.1, SG-0.2, SG-1.9 and
SG-9, so they should not be removable by an UPDATE-shaped mistake in a settings
screen. Every **other** key stays deletable exactly as it was (tests 65, 66).

### The suppression GUC ships unused

`app.guardian_consents_audit_suppressed` follows P1.4's pattern exactly:
transaction-local, read in exactly one place, checked first. **Nothing in this
migration sets it** — there is no backfill, because a consent is a statement a
human made and there is nobody to attribute a manufactured one to.

It exists for the **Phase 3 legacy import**, which will insert historical consent
rows in bulk and must write one summary `migration.backfill` row rather than one
attributed-to-nobody grant per child. Both halves are asserted: the suppression
works (113), and an ordinary grant immediately afterwards is still logged (114).

## The unknown-DOB carve-out, restated (needs Adam)

SG-10 scopes the invariant to a **known** minor
(`people.dob IS NOT NULL AND public.is_minor_dob(dob)`), and says why at length:
read literally, it "would then refuse *every* account whose DOB the club does not
hold — including every ordinary adult self-signup, since `handle_new_user()`
creates the person with `dob` NULL, and including the three
`auth.admin.createUser()` paths the live function-room app already uses."

That carve-out is what keeps apps/web working, and SG-10 itself calls it "a
documented deviation from §1.2's fail-closed principle" that "needs Adam's
agreement under §6.2". It is implemented as written (test 129,
`profile_for_unknown_dob_person_allowed`) and it is one of the two points
SAFEGUARDING.md §6.1 flags as still needing Adam's explicit agreement. The other
— extending SG-2's delete/truncate guards to `guardian_consents` — is implemented
here too, and is recorded in DECISIONS.md as a strengthening.

## The signup path

```
auth.users INSERT
  → on_auth_user_created
    → handle_new_user()                       [SECURITY DEFINER]
        raw_user_meta_data->>'person_id' present, a valid uuid,
        names an existing person, that person has NO profile,
        and has_active_consent(person, 'app_account')?
          YES → insert profiles(person_id = that person)     ← the invite
          NO  → create a fresh person, insert profiles(person_id = it)
      → BEFORE INSERT ON profiles
        → trg_profiles_ensure_person            (P1.2 — no-op here)
        → trg_profiles_sg10_account_eligibility (P1.7)
             known minor AND NOT is_account_eligible → RAISE
```

**Falling through is not the same as refusing**, and SG-10 chose falling through:
"in every other case it creates a new person exactly as it does today." A
self-signup quoting a stranger's person id therefore gets an ordinary, empty
account with a fresh person and a NULL dob — it adopts nothing. What it does
*not* get is somebody else's identity, which is the property that matters.

### A note on `underage_signup_without_consent_refused`

SG-10's test list contains both `underage_signup_without_consent_refused` and
`handle_new_user_ignores_person_id_without_active_consent`. Read strictly against
the same scenario the two pull in opposite directions: if a `person_id` naming a
minor **without** consent is *ignored*, then that signup is not refused — it
produces an ordinary unknown-dob account, which SG-10's own carve-out permits.

Both are implemented, against the scenarios in which each is reachable:

- **Test 141, `underage_signup_without_consent_refused`** — an invited signup
  naming a consented child who is nevertheless **below `min_account_age`**. The
  invite branch adopts, §10's guard raises, and the whole `auth.users` insert
  fails (test 142 asserts the login was rolled back with it). This is the
  reachable "the auth admin path is refused" case, and SG-10's enforcement note
  is explicitly about that path.
- **Tests 143–145, `handle_new_user_ignores_person_id_without_active_consent`** —
  a `person_id` with no consent falls through, adopts nobody, and a fresh person
  is created.
- **Tests 123–125** cover the *direct* auth-admin shape — a profile inserted for
  an under-age person — as the owner and as `service_role`, which is where the
  refusal is unconditional.

No named test is deleted, skipped or marked TODO (§6.3).

## Rollback

The full script is in §15 of the migration. Run as `postgres`, in one
transaction, in this order:

1. Restore `handle_new_user()` to its P1.2 body (the invite branch goes).
2. Restore `people_dob_guard()` to its P1.1 body (the SG-10 block goes, and with
   it `SECURITY DEFINER`).
3. Drop the `profiles` guard and the three `site_settings` triggers.
4. Delete the two seeded settings rows — the **one** circumstance in which they
   may be deleted, and step 3 has just removed the trigger that would refuse it.
5. `drop table public.guardian_consents` — takes its policies, indexes and
   triggers with it, and destroys any consent rows. That is correct for a
   rollback of the migration that created the table, and is the **only**
   circumstance in which a consent row may be destroyed. Audit rows it wrote are
   **not** deleted: audit rows are append-only (SG-2).
6. Drop the twelve functions and the enum, dependants first.
7. Write a `migration.rollback` audit row.
