## The shape of the problem

The live site still deploys from the old repo against this same database
(P0.4's Vercel repoint was deferred), and Claude holds no Vercel credentials.
So "migrate the data and switch the app" cannot be one atomic act: the old app
keeps writing to `room_bookings` until the domain moves. P1.6 therefore ships
**an idempotent sync, not a one-shot copy**, plus the rewritten `apps/web`,
plus a runbook for the moment the domain moves. The legacy tables are
untouched until that moment (rename-to-`_legacy` + read-only views is step 3
of the runbook, and is deliberately *not* in this migration — it would break
the live site the instant it was pushed).

## What the migration does

| Step | Object | Notes |
|---|---|---|
| 1 | SG-2 on `public.audit_log` | `deny_hard_delete()` + `deny_truncate()`; DELETE/TRUNCATE revoked from anon/authenticated/**service_role**. The SAFEGUARDING §4 "Audit (Phase 1 review)" item. Policy set unchanged. |
| 2 | `public.write_audit(action, entity, entity_id, detail)` | §4's single helper. SECURITY DEFINER; actor from `auth.uid()`, email from `auth.users`; blank action/entity → `22023`. authenticated + service_role; anon revoked by name. |
| 3 | `public.booking_comms` | Generalised `booking_emails`: `channel` (`email`/`sms`/`push`/`in_app`), `to_address`, `legacy_booking_email_id`. RLS: staff+club_admin read/insert, booker self-read, `TO authenticated`; authenticated has no UPDATE/DELETE grant (a sent message is a record). |
| 4 | `public.migrate_room_bookings()` | Upsert by `legacy_*_id` into `resources` ← `function_rooms`, `bookings` ← `room_bookings`, `payments` ← `booking_payments`, `booking_comms` ← `booking_emails`; then delete unified copies whose legacy row was hard-deleted (cascade takes payments/comms). Refuses (`P0001`) any `status` / `payment_status` value outside the enums rather than guessing. One `migration.backfill` / `bookings` audit row per run with the five counts. service_role only. |
| 5 | `public.reconcile_room_bookings()` | 18+ `(check, legacy, unified, ok)` rows: four row counts, `sum(amount_pence)`, `sum(total_pence)`, status ×5, payment_status ×3, kind=block, payment/comm linkage to the *same* booking, profile→person link, Europe/London round-trip of every date/time, overnight count. service_role only. |
| 6 | Run + gate | Runs 4, then raises listing every failed check of 5, so a bad reconciliation rolls the whole migration back. |

### Conversions

- `starts_at = (date + start_time) at time zone 'Europe/London'`;
  `ends_at` likewise with `+ 1 day` when `end_time < start_time` (the baseline
  constraint's own overnight rule; 7 prod rows). Monotonic, so every pair that
  satisfied `room_bookings_no_overlap` satisfies `bookings_no_overlap`.
- `booking_type 'block'` → `kind 'block'`; everything else → `'hire'`.
- `booker_person_id` = `profiles.person_id` of `booker_profile_id` (30 of 40
  prod rows). **No `people` row is created for the 10 walk-in hirers**: a hire
  contact snapshot is not a member record, and P1.2's never-match-on-email rule
  applies with equal force.
- `function_rooms.resources` → `resources.amenities`.
- `room_bookings.amount_pence` has no unified column (the app derives it from
  `total_pence`/payments); every other legacy column keeps its name.

## apps/web

The data layer moves to `resources` / `bookings` / `payments` with
`Database` types from `@club/db`; UI keeps working in Europe/London
date + time via `src/lib/booking-time.ts`; the manual overlap pre-check becomes
`rpc('booking_has_conflict')` plus handling of `23P01`; the dead `events`
query goes; `noUncheckedIndexedAccess` is back on. Role gating
(`profiles.role`, `isStaff()` …) is unchanged — that is Phase 4's move. See
the PR description for the file list.
