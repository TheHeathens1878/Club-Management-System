# P1.2 — `profiles.person_id`

`supabase/migrations/20260822110000_profiles_person_link.sql`

## What it does

Joins the three layers of identity: `auth.users` (the credential) →
`public.profiles` (the app account) → `public.people` (the human, P1.1).

| Object | Purpose |
|---|---|
| `public.profiles.person_id` | `uuid not null`, `unique`, `references public.people(id) on delete restrict`. The one-to-one link. |
| `public.split_person_name(text)` | IMMUTABLE. Returns `(first_name, last_name)`. Last token is the surname; everything before it is the forename(s); a single token gets `last_name = '(unknown)'`; no usable name gives two `'(unknown)'`s. |
| `public.backfill_profiles_people()` | SECURITY DEFINER. Creates one `people` row per unlinked profile and links it. Returns `(profiles_linked, people_created, people_ids)`. Idempotent — the driving query is `where person_id is null`. |
| `public.profiles_ensure_person()` | `before insert on public.profiles`, SECURITY DEFINER. If `person_id` is null: adopt the existing profile's person (upsert case) or manufacture one. **Load-bearing — see below.** |
| `public.handle_new_user()` | Replaced. Creates the person first, then the profile carrying its id. Same signature, same `on conflict (id) do nothing`, same default role. |
| `people_self_read` | The policy P1.1 left as a marked TODO in its §7. A user may select exactly their own `people` row. No self-update. |
| `audit_log` | One `migration.backfill` row: `actor_id` null, `actor_email` `'migration'`, `entity` `'profiles'`, `detail` = `{migration, profiles_linked, people_created, people_ids}`. |

Additive only (PLAN §2.5): no existing `profiles` column is dropped or renamed.
`role`, `full_name`, `created_at`, the four `bar_*` columns and
`holiday_allowance_days` are untouched, so apps/web continues to read and write
them unchanged.

## Decisions

**NOT NULL, set in this migration.** The alternative — "nullable during the
transition" — means forever: no later task would ever be entitled to tighten it,
and every consumer from P1.3 on would carry a null branch that must never be
taken. The migration backfills, asserts `count(profiles where person_id is null)
= 0` and `count(people) >= count(profiles)` in a `do $$ ... raise exception`
block that fails the migration if either is violated, and only then sets NOT
NULL.

**A plain `UNIQUE` constraint, not a partial unique index.** A partial index
`where person_id is not null` is the right shape only while nulls are possible.
Once the column is NOT NULL the predicate is tautological — it costs a reader a
moment working out why it is there, and it cannot be referenced by a future
foreign key. The constraint's index serves the `people → profiles` direction, so
no separate index is added.

**`on delete restrict`, and why it is the second line of defence.** P1.1
attached `deny_hard_delete()` / `deny_truncate()` to `public.people` and revoked
DELETE/TRUNCATE from all three API roles, so a person cannot be hard-deleted at
all. RESTRICT is what would still speak up if that trigger were ever disabled.
The reverse direction is deliberately asymmetric: `profiles.id references
auth.users on delete cascade`, so deleting an auth user still removes the profile
and leaves the person row standing — the club's record of a human outlives their
login.

**Single-token names get `last_name = '(unknown)'`.** `people` has
`check (btrim(last_name) <> '')`, so the empty string is unavailable. Repeating
the token into both fields would fabricate a surname that then propagates into
correspondence and team sheets. `'(unknown)'` is conspicuous, greppable, and
sorts every affected row together in a list ordered by last name — which is the
cleanup queue. The split is deliberately naive ("van der Berg", "Dr A Patel"
come out imperfectly): it produces a starting value for a field a human will
correct, and it is applied only to legacy `full_name` strings and signup
metadata, never to a name typed into a form with two boxes.

**No auto-link by email — a safeguarding rule, not a convenience choice.**
`handle_new_user()` always creates a *new* person. It never looks for a `people`
row with a matching email and attaches to it, and neither does
`profiles_ensure_person()`. Families share an email address, and P1.1's own
design note says a minor's contact route is their guardian — so a child's record
may legitimately carry a parent's address. Matching on it would hand a brand-new
login somebody else's identity together with everything that hangs off it:
guardianships (P1.3), roles (P1.4), certifications (P4.3), conversations (P5.2).
A duplicate person is a tidy-up; a wrongly merged person is a safeguarding
incident. Merging is an administrative act with a human decision behind it and
gets a deliberate tool later. Recorded in `DECISIONS.md`.

**The backfill copies `created_at` from the profile, leaves `dob` null and
`created_by` null.** `dob` null means minor (SG-0): nobody should be presumed an
adult on the strength of having had a login on the old function-room app.
`created_by` null because a migration is not a person's act. `created_at` from
the profile because the human has existed at least as long as their account.

**Email is copied defensively.** `auth.users.email` is unique and
`people_email_unique_live_idx` is unique on `lower(email)` among live rows, so a
collision should be impossible. Three things make "impossible" insufficient: a
person row may already exist from another source (the Phase 3 Neon import lands
in the same table), `auth.users.email` is nullable (phone-only signups), and
`people_email_format` is stricter than Supabase's own validation. Rather than
abort — which would take the whole migration, or a live signup, with it — the
email is dropped to NULL and the person is still created. `people.email` is
nullable and the partial index permits any number of NULLs.

**`trg_profiles_ensure_person` is what makes NOT NULL compatible with
apps/web.** Three server actions upsert into `profiles` immediately after
`auth.admin.createUser()`:

| File | Payload |
|---|---|
| `apps/web/src/app/book/actions.ts:25` | `{ id, role, full_name }` |
| `apps/web/src/app/(app)/super-users/actions.ts:118` | `{ id, role, full_name }` |
| `apps/web/src/app/(app)/settings/actions.ts:225` | `{ id, role, member_id, password_set, full_name }` |

PostgREST renders each as `insert into profiles (...) values (...) on conflict
(id) do update set ...`. The profile already exists by then, so the statement
resolves to the UPDATE branch — but **Postgres evaluates the table's constraints
against the proposed tuple before it arbitrates the conflict.** Verified against
the local database:

```
insert into t (id, a) values (1, 'z') on conflict (id) do update set a = excluded.a;
ERROR:  null value in column "b" of relation "t" violates not-null constraint
```

So a bare NOT NULL would break the invite, staff-account and booker-account
flows. P1.2's acceptance criterion is "room booking app unaffected", so the
constraint is made *satisfiable* rather than the app made to change. The trigger
first looks for an existing profile with the same id and adopts its `person_id`
— that branch is the one that matters, since manufacturing a fresh person there
would leak one orphan per upsert — and only creates a person when the profile is
genuinely new. On an ordinary signup `handle_new_user()` has already set
`person_id`, so the trigger sees a non-null value and does nothing.

**`people_self_read`, and no self-update.** The policy is P1.1's comment made
real. The subquery runs as the caller, so `profiles`' own RLS
(`profiles_self_read`) applies and it can only ever resolve to the caller's own
`person_id`; there is no recursion, because the `profiles` policy does not
reference `people`. A self-*update* is deliberately absent: SG-0 derives minority
from `people.dob`, so a self-service dob edit is a self-service exit from every
child-protection rule in `SAFEGUARDING.md`. If Adam wants members to maintain
their own contact details, that is a column-scoped policy (email/phone/address/
preferred_name only) plus a `people_dob_guard()` extension — a P1.4 decision.

## SG invariants

| Invariant | Position |
|---|---|
| **SG-0** | Consumer, not implementer. The link makes `is_minor(person_id)` answerable for a logged-in user for the first time. Backfilled people get `dob = null`, i.e. minor — fail closed. |
| **SG-2** | Nothing new, and nothing weakened. No `FOR DELETE` policy is added anywhere. One behavioural change worth recording: because `profiles.person_id` now references `people`, a bare `truncate public.people` fails `0A000` (referenced by a foreign key) *before* the `BEFORE TRUNCATE` trigger fires. `truncate public.people cascade` still reaches the trigger and still raises `P0001`. Both forms are asserted in `people_rls.test.sql`. The SG-2 guard for `public.audit_log` itself remains a separate small Phase 1 migration and is deliberately not smuggled in here. |
| **No auto-link by email** | New rule, decided here, recorded in `DECISIONS.md`, enforced by the absence of any email lookup in `handle_new_user()` / `profiles_ensure_person()` and tested in section F of `profiles_person_link.test.sql`. |

already linked, with names split correctly for two-, three-, one- and zero-token
names, the email copied, `dob` null, `created_at` inherited and no person shared
between logins (C); that two profiles cannot point at one person and that

accepted because the guard supplies one (D); the apps/web upsert regression, and
that it creates no orphan person (E); no auto-link by email, including that a
colliding email is dropped rather than aborting the signup (F); `people_self_read`
returning exactly the caller's own row and nothing of anyone else's, for two
different users (G); that deleting a referenced person is refused — `42501` as
`service_role` (privilege revoked) and `P0001` as the table owner (the SG-2
trigger, which fires before RESTRICT is reached) (H); the audit row's contents
and conventions, that a second `backfill_profiles_people()` call returns
`(0, 0, {})` and writes no further audit row, and that a profile whose
`person_id` is nulled (with NOT NULL dropped and restored inside the test
transaction — no trigger is disabled) is re-linked with `(1, 1)` and the correct
split (I); and that no API role holds EXECUTE on any of the three new functions
(J).

The changes to `people_rls.test.sql` are the honest consequences of the link

rather than 2 (two fixtures plus one person per login), and the owner-truncate
assertion is split into the `0A000` and `P0001` cases described above.

Same two footnotes as P1.1: `db lint` is scoped to `--schema public` (unscoped it
lints pgTAP's own function bodies), and `gen types --local` needs
`SUPABASE_DB_PASSWORD=postgres` because the project is linked. The generator's
`--local` output omits the four-line hand-written header and the
`__InternalSupabase` / `PostgrestVersion` block that `--linked` emits; both are
re-applied by hand so the committed diff stays purely additive. This regeneration
adds `person_id` to `profiles`' `Row`/`Insert`/`Update`, the
`profiles_person_id_fkey` relationship, and the two new callable functions.
apps/web's Supabase clients are created untyped (`createClient(url, key)` with no
`<Database>` parameter), so the now-required `person_id` in the `Insert` type does
not affect its typecheck.

## Rollback

Full statements are in §11 of the migration, including the previous
`handle_new_user()` body verbatim. In order: restore `handle_new_user()`, drop
`trg_profiles_ensure_person`, drop `people_self_read`, **soft-delete** the
backfilled people, drop the column (which takes the unique constraint and the FK
with it), drop the three functions, write a `migration.rollback` audit row.

The people rows are identified from `audit_log.detail -> 'people_ids'` — the
reason the backfill function returns the ids at all. No timestamp windows, no
name patterns, no marker column polluting the data model. The delete is soft
because `trg_people_deny_hard_delete` raises `P0001` for every role including the
owner, and disabling it is exactly what `SAFEGUARDING.md` §3 SG-2 forbids. Soft
deletion also releases the rows' emails from `people_email_unique_live_idx`
(partial on `deleted_at is null`), so re-applying the migration afterwards works
and simply creates a fresh set of person rows.
