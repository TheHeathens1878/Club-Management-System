# P1.5 — `resources`, unified `bookings`, generalised `payments`

`supabase/migrations/20260823100000_resources_bookings.sql` · Linear TH1-14 ·
branch `phase-1/p1.5-resources-bookings`

## What it does

Three new tables, four enums, one exclusion constraint, two conflict-check
functions, one trigger. Nothing legacy is touched: `function_rooms`,
`room_bookings`, `booking_payments` and `booking_emails` are byte-identical to
the baseline and the live function-room app keeps writing to them. P1.6 moves
the data and the app together.

| Object | Purpose |
|---|---|
| `public.resource_type` | `function_room`, `pitch`. A third kind is one `alter type … add value`. |
| `public.booking_status` | `enquiry`, `quoted`, `pending`, `confirmed`, `cancelled` — exactly the five values prod's `room_bookings.status` holds (census 2026-08-23: 11/19/8/1/1). |
| `public.payment_status` | `unpaid`, `deposit_paid`, `paid` — prod's three. |
| `public.booking_kind` | `hire` (default), `block` (the staff block-booking action writes this today), `fixture` (P2.5), `maintenance`. |
| `public.resources` | Every bookable thing. Pricing/extras columns of `function_rooms` carried as nullable typed columns; `resources text[]` renamed `amenities`; `default_pre/post_buffer_minutes` for P2.5; `legacy_function_room_id` for P1.6's reconciliation. |
| `public.bookings` | Half-open `[starts_at, ends_at)` in `timestamptz`, buffers in minutes, `[blocked_from, blocked_until)` trigger-maintained, plus every non-derivable `room_bookings` column under its own name so P1.6 is a rename, not a redesign. `booker_person_id` (→ `people`) and `booker_profile_id` (→ `profiles`) both nullable; contact snapshot columns NOT NULL. `legacy_room_booking_id` for reconciliation. |
| `public.payments` | `booking_payments` with `booking_id` → `bookings`, a `stripe_payment_intent_id` column for P4.1, and `legacy_booking_payment_id`. |
| `bookings_no_overlap` | The baseline GiST pattern: `resource_id WITH =`, `tstzrange(blocked_from, blocked_until, '[)') WITH &&`, `WHERE status IN ('pending','confirmed')`. |
| `booking_conflicts(...)` / `booking_has_conflict(...)` | Same filter, same half-open range, optional `p_exclude_booking_id`. SECURITY INVOKER. |

## Decisions

1. **Timestamps, not `date + time`.** The legacy "end earlier than start means
   tomorrow" convention is a function-room idiom; a pitch allocation from a
   Full-Time kickoff is a timestamp. P1.6 converts with `(date + time) at time
   zone 'Europe/London'` and the app formats in Europe/London.
2. **The blocked window lives in two trigger-maintained columns.** Generated
   columns and index expressions both require IMMUTABLE; `timestamptz ±
   interval` is STABLE. The trigger fires on any write to the six inputs
   including the two outputs, so a client cannot supply its own window
   (tested). `bookings_blocked_valid` asserts the window contains the period.
3. **Typed columns, not jsonb, for the function-room fields.** Moving a live
   app onto this table is reviewable column by column; a `details jsonb` would
   hide the mapping. A pitch leaves them NULL. `payment_method` (never read or
   written by the app; 1 prod row has `cash`) is kept for reconciliation.
4. **Named `payments`, not `booking_payments`.** The legacy table owns that
   name until P1.6 renames it, and P4.1's ledger is this table with
   `booking_id` nullable beside a subscription reference — not a second table.
5. **RLS via `has_any_role(array['staff','club_admin'])`** mirrors
   `is_staff()`'s reach in the new model (P1.4 mapped every bar/bar_manager/
   staff/committee/super_user profile). SAFEGUARDING §1.3's "staff have no
   inherent access to member or child data" is respected: a booking is a hire
   record and a hirer is "deliberately isolated". `bookings_booker_read` /
   `payments_booker_read` are new: the portal can stop reading via
   `service_role` once P1.6 sets `booker_person_id`.
6. **No SG-2 guard.** Bookings and payments are not in SG-2's list, the staff
   app hard-deletes cancelled enquiries, and staff may delete manual payments
   today (SumUp ones are refused in code). DELETE is `club_admin` only here —
   narrower than legacy `booking_payments_staff_all` — since the app enforces
   in code via `service_role` anyway. P4.1 decides whether payments become
   append-only.
7. **No anon write, anon reads active resources.** The hire form is a server
   action on `service_role` today and stays so; `booking_has_conflict` is not
   granted to anon because as SECURITY INVOKER it would always return false
   for anon (no bookings visible) — a misleading answer is worse than none.
   If a public "is this slot free?" is wanted, P1.6 adds a SECURITY DEFINER
   wrapper that returns only the boolean.
