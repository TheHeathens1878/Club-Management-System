# P1.3 — `public.guardianships`

`supabase/migrations/20260822120000_guardianships.sql`

## What it does

Creates the link that carries authority over a specific child. `SAFEGUARDING.md`
§1.3 is emphatic that this, not the `parent` role, is where that authority lives:
*"The role is a label; only the link (P1.3) carries authority over a specific
child. Every rule below keys off the link, never the role."* Nothing in the
migration reads a role to decide authority over a child.

| Object | Purpose |
|---|---|
| `public.current_person_id()` | STABLE, SECURITY DEFINER, `search_path = public`. `auth.uid()` → `profiles.id` → `profiles.person_id`. NULL for `anon` and for a JWT with no profile. **The helper every policy from here on uses.** |
| `public.guardian_relationship` | Enum: `parent`, `step_parent`, `grandparent`, `foster_carer`, `legal_guardian`, `other`. |
| `public.guardianships` | `guardian_person_id` → `people(id)` and `child_person_id` → `people(id)`, both `on delete restrict`; `relationship`; `notes`; `ended_at`; `created_at` / `updated_at` / `created_by`. |
| `public.guardianships_guard()` | `before insert or update of guardian_person_id, child_person_id` — the SG-4 age and self tests. |
| `public.guardianships_conversation_guard()` | `before delete or update of guardian_person_id, child_person_id, ended_at` — the SG-1.8 guard. **Scaffolded**: the trigger is real, the body is a no-op while `public.conversations` does not exist. P5.2 replaces the body. |
| `trg_guardianships_deny_truncate` | P1.1's generic `deny_truncate()`. There is deliberately **no** `deny_hard_delete()` here — see below. |
| `trg_guardianships_updated` | The baseline `set_updated_at()`. |
| Indexes | `guardianships_active_pair_idx` — unique on `(guardian_person_id, child_person_id)` **where `ended_at is null`**; `guardianships_child_idx`; `guardianships_guardian_idx`. |
| RLS on `guardianships` | Five policies: `guardianships_guardian_read` (own links), plus committee read / insert / update / **delete**. |
| `people_guardian_read` | New policy on `public.people`: a guardian reads a child's person row via a **live** link, **while the child is still a minor**. |
| Grants | `revoke all` from the three API roles, then `select, insert, update, delete` to `authenticated` and `service_role`; nothing to `anon`; `truncate` revoked from all three and named explicitly. |

## SG invariants

| Invariant | How this migration satisfies it |
|---|---|
| **SG-4** (guardianship integrity) | In full. Child minor at creation, guardian an adult **with a known DOB**, guardian ≠ child, no duplicate live link, and the RLS SG-4 specifies. Every violation is attempted and rejected in `guardianships.test.sql` §D–§F. |
| **SG-1.8** (guardianship-change guard) | Scaffolded exactly as SG-1's *"Implemented by"* paragraph directs. The trigger, its timing (`BEFORE`, `FOR EACH ROW`) and its column list ship now and are asserted by the tests; only the body is deferred. |
| **SG-2** (soft delete only) | **Deliberately asymmetric.** The TRUNCATE half applies; the hard-DELETE half does not, and must not — see below. |
| **SG-0** | Consumer only. Every age question goes through P1.1's `is_minor()` / `is_minor_dob()`; nothing is re-implemented. |
| **SG-7** | **Not satisfied, knowingly.** See "Open gap" below. |

## Decisions

### Hard DELETE stays available — the exact spec lines

This is the decision most likely to look wrong at a glance, so the citations
come first.

SG-2's statement names four tables and this is not one of them:

> "No row in `messages`, `audit_log`, `safeguarding_concerns`, or
> `conversation_participants` may ever be hard-deleted, by any role, including
> `service_role`."

And SG-1.8 requires the DELETE to remain possible, in terms, as part of its own
design:

> "Why 'reject unless closed' rather than a flat reject: a flat reject makes a
> mistyped or genuinely-ended guardianship permanently unremovable, which is
> itself a data-protection problem. Requiring the conversations to be closed
> first gives the administrator a deliberate two-step sequence — close the
> conversation, then remove the link — and preserves the message history for
> SG-8."

Attaching `deny_hard_delete()` here would *be* that flat reject. It would make
SG-1.8's specified two-step sequence impossible and would leave a link typed
against the wrong child standing forever, which is a worse record than none. So
the guard on deletion is SG-1.8's conditional one, not SG-2's unconditional one,
and `DELETE` is granted to `authenticated` and `service_role` with a
`FOR DELETE` policy gated on `is_committee()`.

`service_role` holds `DELETE` on purpose. SG-1.8:

> "All four run as `club_admin` **and** as `service_role`, since SG-4's RLS is
> what grants the write and the trigger is what must survive the bypass."

That test is only meaningful if the privilege is present for the trigger to be
the thing that refuses.

**TRUNCATE is refused, which is a strengthening beyond SG-2's literal table
list.** A row-level `BEFORE DELETE` trigger does not fire on `TRUNCATE` — SG-2's
own reasoning — so one statement would strip every guardian link in the club
without the SG-1.8 guard being consulted once: the prohibited state SG-1.8
exists to prevent, applied to every child at the same moment. There is no
administrative act that `TRUNCATE` serves and a targeted `DELETE` does not.
`SAFEGUARDING.md` §6.2 permits strengthening without Adam's agreement and asks
that it be recorded; it is, in `DECISIONS.md`.

### The SG-1.8 scaffold — the exact spec lines

SG-1 "Implemented by":

> "Where P1.3 lands before the messaging tables exist, the SG-1.8 trigger is
> written in P1.3 as a no-op-if-absent guard and completed in P5.2; the P5.2 PR
> is not complete without its tests."

And SG-4's enforcement list:

> "**Trigger for guardianship *changes*, not only creation.** … The
> `BEFORE DELETE` / `BEFORE UPDATE OF guardian_person_id, child_person_id` guard
> is specified in full at **SG-1.8**, lives on this table, and ships with P1.3 —
> not with P5.2."

So P1.3 owns the trigger's existence, timing and column list; P5.2 owns the
body. The body today is one `to_regclass` test:

```sql
if to_regclass('public.conversations') is null then
  return case when tg_op = 'DELETE' then old else new end;
end if;

raise exception 'guardianships: public.conversations exists but the SG-1.8
  guard has not been completed; P5.2 must replace
  public.guardianships_conversation_guard() …';
```

The `raise` in the second branch is the point of the design, not decoration.
While the messaging tables are absent there is no conversation to protect and
the change goes through. The moment `public.conversations` exists and this body
has *not* been replaced, the guard refuses rather than waving changes past —
fail closed (§1.2), and a forcing function: P5.2 cannot create `conversations`
without also completing this function, because its own migration would otherwise
be unable to touch the table.

**One addition to SG-1.8's column list: `ended_at`.** SG-1.8 names DELETE and
`UPDATE OF (guardian_person_id, child_person_id)`; it was written before this
table had an `ended_at` column. A retired link cannot be what makes an
adult↔minor 1:1 permissible, so for SG-1 purposes ending a link is
indistinguishable from deleting it — and leaving it out would be a hole with a
soft edge: an administrator blocked from deleting the row could simply end it
instead and reach the same prohibited state. Strengthening again; recorded in
`DECISIONS.md`. **P5.2's completed body must honour it**: an `ended_at`
transition from NULL to non-NULL is evaluated exactly as a delete of the pair.

### The SG-4 guard fires on INSERT and on retarget only

SG-4 scopes its statement to creation — *"valid only if, **at creation**"* — and
then says so again:

> "**The link outlives the minority.** When the child turns 18 the row is **not**
> invalidated or deleted — the age tests apply at creation only."

A guard on `BEFORE INSERT OR UPDATE` (all columns) would contradict that
directly: the day after the child's 18th birthday, setting `ended_at` — the
ordinary act of closing the arrangement — would re-run the "child must be a
minor" test against an adult, be refused, and freeze the row forever. So the
trigger is `BEFORE INSERT OR UPDATE OF guardian_person_id, child_person_id`, and
the UPDATE branch additionally requires that a party actually changed
(`IS DISTINCT FROM`), because `UPDATE OF col` fires whenever the column appears
in the `SET` list even at the same value.

That is precisely SG-1.8's retarget rule: *"A retarget is evaluated as a delete
of the old pair plus an insert of the new pair: the old pair is checked as
above, and the new pair must independently satisfy SG-4."* `guardianships_guard()`
is the second half; `guardianships_conversation_guard()` is the first.

This is a deviation from the P1.3 task description, which asked for `BEFORE
INSERT OR UPDATE`. `SAFEGUARDING.md` §1 settles it: *"Where this document and a
task description disagree, this document wins and the task must be
re-specified."* Same precedent as P1.1's refusal of the `people_staff_read`
policy.

### The guardian's DOB must be known; the child's need not

SG-4:

> "**Deliberate asymmetry — the guardian's DOB must be known.** SG-0 treats
> unknown DOB as a minor, so an unknown-DOB 'guardian' fails the adult test and
> the link is rejected. This is intended: a guardianship record with an
> unidentified adult is not a safeguarding control."

The guard therefore tests `dob is not null` *and* `not is_minor_dob(dob)` for
the guardian, with two different messages, because the two failures need
different actions from the administrator ("find out this person's date of birth"
versus "this person cannot be a guardian").

For the child it calls `public.is_minor(child)`, which is TRUE for a NULL dob
(SG-0), so a child whose date of birth is unknown **is accepted**. That is the
protective direction: refusing would leave the child the club knows least about
with no recorded guardian at all. Fail-closed producing opposite-looking answers
on the two sides is the same rule — *treat the unknown as a child* — landing
correctly in both places.

### Partial unique index, not a full `UNIQUE`

SG-4 asks for `UNIQUE (guardian_person_id, child_person_id)`. The migration
implements `unique (guardian_person_id, child_person_id) where ended_at is null`.

SG-4 was written before this table had an `ended_at` column, and a full UNIQUE
is incompatible with a soft end in a way that damages the record: once a foster
placement is ended, that carer could never be recorded as the child's guardian
again, and the only way to express a resumed arrangement would be to clear
`ended_at` on the old row — erasing the gap, which is exactly the history a
safeguarding record exists to hold. Restricting uniqueness to live rows keeps
SG-4's actual intent (no two simultaneous live links for one pair, so "is X the
guardian of Y?" always has one answer) and makes the honest record possible.

The two are not equivalent, so **this is flagged for Adam under §6.2** rather
than treated as a free refinement. Tested both ways: a duplicate *live* link is
rejected `23505`, and an ended link followed by a new one is allowed.

### Guardian access lapses at 18 — the D5 default

SG-4:

> "Its **effects** lapse: guardian access to the young person's data ends at 18
> (or at a transition age — Open Decision D5), which is enforced in the reading
> policies, not by mutating the guardianship row."

Open Decision D5 is unresolved and explicitly needs Adam's view, so
`people_guardian_read` implements the invariant's stated default — straight to
zero at 18 — as `public.is_minor(people.id)` in the `USING` clause, alongside
`g.ended_at is null`. The guardianship row is untouched by the birthday; only
what it lets its holder read changes, which is what SG-4 asks for. Changing it
later (an age-16 cutoff, a column-scoped view) is a one-policy migration, which
is why the rule lives in the policy rather than in any materialised flag.

The read is `SELECT` only. A parent may not edit their child's record, least of
all `dob`, for the same reason P1.2 refused a self-update: SG-0 is load-bearing
and a DOB change is an administrative act. Registration data is captured through
the P2.2 flow with the club as writer.

### A child does not see their own guardianship rows

Guardian and committee only. Reasoning:

* A minor reading "Jane Smith is recorded as your foster carer" is usually
  harmless and arguably their right. In the case that matters — a contested
  arrangement, a parent without contact — the same row tells a child something
  the club is not the right body to be telling them, and `notes` may carry the
  shape of a court order.
* §1.3 derives parental authority from the link and says nothing about the
  child's own sight of it. Inventing a read here would be inventing policy in a
  migration.
* **D5 is the decision that settles this too**: whatever transition age D5 lands
  on is the age at which a young person should see, and be able to question, the
  links held over them.

Adding the policy later is one migration; removing a read a child has already
had is not. A minor is not shut out of the *fact* of their own record —
`people_self_read` (P1.2) still shows them their own person row.

### An enum, not `text` + `CHECK`

The set is small and closed; the generated TypeScript becomes a real union
rather than `string`, so an invalid relationship is a compile error in the web
and mobile apps as well as a database error; and `CHECK (relationship in (…))`
costs the same `ALTER TABLE` to extend while giving the app nothing.

Extend with `alter type public.guardian_relationship add value 'special_guardian';`
in a new migration. Since PG12 that may run inside a transaction block (so an
ordinary CLI migration is fine) but the new value cannot be *used* in the same
transaction — add the value in one migration, reference it in the next. Values
cannot be removed or renamed in place.

`other` exists so an unusual arrangement is recorded truthfully with detail in
`notes`, rather than being forced into `legal_guardian` because that is the
nearest available lie. Nothing in the schema treats `other` differently: SG-4
and SG-1.8 key off the existence of the link, never the relationship type.

### `current_person_id()`

SECURITY DEFINER, matching `is_committee()` and `is_minor()`: a caller must be
able to resolve their own person without holding a read on `public.profiles`.
Returns NULL for `anon` and for a JWT whose subject has no profile — every
policy then compares a NOT NULL column against NULL, which yields NULL, which
RLS reads as "no". Fail closed. `EXECUTE` is revoked from `PUBLIC` **and from
`anon` by name** (the P1.1 preview-branch lesson: hosted Supabase's default
privileges grant EXECUTE on every new function to all three API roles
explicitly, which `revoke … from public` does not touch).

It is not an oracle: it discloses only the caller's own person id, which
`people_self_read` already lets them read.

### Error reporting

Every `raise` is `P0001` (plpgsql's default) with a distinct, self-explaining
message naming the invariant. No custom SQLSTATEs: PostgREST surfaces the
message either way, a bespoke five-character class would have to be documented
and remembered in three languages, and P1.1 set the house precedent
(`people_dob_guard()`, `deny_hard_delete()`, `deny_truncate()` are all `P0001`).
The tests assert the code **and** the message text, so the messages are part of
the contract.

One firing-order note, because it is not obvious: a `BEFORE ROW` trigger runs
*before* the table's `CHECK` constraints are evaluated, so a self-guardianship
raises `P0001` from the trigger and `guardianships_not_self` is never reached in
practice. The constraint is not redundant — it is the layer that still holds if
the trigger is disabled or dropped, which is exactly what SG-4 means by "a plain
constraint, always true". The test asserts both.

## Open gap: SG-7

SG-7 requires an audit row for *"any read of `guardianships` outside a guardian's
own links"* — i.e. every committee read added by this migration. Postgres has no
SELECT trigger, which is why SG-7's own enforcement note makes those reads
`SECURITY DEFINER` accessor functions that write their audit row before
returning, with no direct table grant behind them. That pattern (and
`public.write_audit()`, per §4) arrives with **P4.3**. Until then the
`guardianships_committee_read` policy is an open SG-7 gap. It is recorded here
and in `DECISIONS.md` rather than silently left; closing it early would mean
inventing the accessor convention two tasks ahead of the task that owns it.

## Rollback

Run as `postgres`, in one transaction, in this order. Nothing is destructive of
anything but this migration's own objects: the table is new and empty and no
backfill runs.

```sql
drop policy if exists "people_guardian_read"           on public.people;
drop policy if exists "guardianships_guardian_read"    on public.guardianships;
drop policy if exists "guardianships_committee_read"   on public.guardianships;
drop policy if exists "guardianships_committee_insert" on public.guardianships;
drop policy if exists "guardianships_committee_update" on public.guardianships;
drop policy if exists "guardianships_committee_delete" on public.guardianships;
drop trigger if exists trg_guardianships_guard              on public.guardianships;
drop trigger if exists trg_guardianships_conversation_guard on public.guardianships;
drop trigger if exists trg_guardianships_updated            on public.guardianships;
drop trigger if exists trg_guardianships_deny_truncate      on public.guardianships;
drop table if exists public.guardianships;
drop function if exists public.guardianships_guard();
drop function if exists public.guardianships_conversation_guard();
drop function if exists public.current_person_id();
drop type if exists public.guardian_relationship;
```

`drop table` would remove its own triggers, indexes and policies; they are
listed explicitly because PLAN §11 asks for a rollback that can be read and
reasoned about, and because `people_guardian_read` lives on a table this
migration does not drop. `current_person_id()` comes after the policies that
reference it.
