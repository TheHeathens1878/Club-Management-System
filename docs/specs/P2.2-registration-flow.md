# P2.2 — Registration flow specification

Status: implemented in `20260823130000_registrations.sql` (schema + rules);
the web/mobile screens that drive it are P6.2 / a later web task. This
document is what those screens must do, and why.

## 1. Who registers whom

| Subject | Submitted by | DB rule |
|---|---|---|
| Adult (known DOB, 18+) | themself, or a `club_admin` on their behalf | `registrations_guard()` INSERT branch; policies `registrations_self_insert` / `registrations_admin_insert` |
| Minor (incl. **unknown DOB**, SG-0) | an **active guardian** (`guardianships.ended_at is null`), or a `club_admin` typing in a paper form | guard checks the link — never the `parent` role (SAFEGUARDING §1.3); policy `registrations_guardian_insert` |
| Anyone, via the Phase 3 import | `service_role` (no `auth.uid()`) | guard passes; `submitted_by` NULL is honest |

One live (pending/approved) registration per person per season
(`registrations_live_idx`). A rejected or withdrawn one is final; register
again with a new row.

## 2. What the form captures

`registrations.form jsonb` (`form_version` says which shape). Version 1:

```json
{
  "emergency_contact": { "name": "", "phone": "", "relationship": "" },
  "medical": { "conditions": "", "medication": "", "allergies": "" },
  "previous_club": "",
  "preferred_position": "",
  "kit_size": "",
  "terms_accepted_at": "2026-08-01T10:00:00Z",
  "terms_version": "2026-1"
}
```

`form` is **sensitive**. Read policy: the subject, their active guardians,
`club_admin`, `safeguarding_lead`. **Coaches cannot read it** — pitch-side
access to a medical note is a Phase 4 audited accessor (SG-7), not a table
read. `audit_log.detail` never carries the form (tested).

## 3. Consents for a child — captured at the same moment

For a minor, the registration screen shows the guardian **four separate**
photo decisions (D4, SG-5) and, where relevant, the two account decisions
from P1.7. Each "yes" is one `guardian_consents` row; each "no" is **no row**
(absence = refused, fail closed):

| Checkbox | `consent_type` | `expires_at` |
|---|---|---|
| Team album (private, team only) | `photo_team_album` | season `ends_on` 23:59 Europe/London |
| Club website / public gallery | `photo_club_website` | season end |
| Club social media | `photo_social_media` | season end |
| Press / local media | `photo_press` | season end |
| App account for the child (P1.7, SG-10) | `app_account` | NULL (until D12) |
| Unsupervised 1:1 messaging with adults, 14+ (P1.7, SG-1.9) | `unsupervised_messaging` | NULL (until D12) |

Rules the DB already enforces (P1.7 guard, reused unchanged): the granter
must be an adult with a known DOB holding an **active** guardianship to the
child; `notice_version` is mandatory (the screen passes the id of the consent
wording shown, e.g. `photo-2026-1`); a consent is immutable — withdrawal is
`revoked_at`, and re-consent is a new row. Every grant/withdrawal writes
`safeguarding.consent.granted` / `.revoked` (SG-7).

Per-season expiry is why re-registration re-asks every year: a consent given
two seasons ago is not evidence of a current decision (D12 reasoning).

Adults' own photo preferences are outside SG-5 and are captured in
`form.photo_preferences` (informational).

## 4. Decision

`club_admin` approves or rejects (`registrations_admin_update`;
`decided_at`/`decided_by` stamped by the trigger, `decision_note` free text).

**Approval with a `team_id` creates the live `team_memberships` (player) row
for the season.** That means P2.1's SG-6 composition guard runs at the moment
of approval: approving a child onto a team whose coach has no in-date DBS /
safeguarding qualification **fails**, naming the coach, and the registration
stays pending. The screen must surface that message verbatim — it is the
administrator's to-do list, and the only correct fix is a certification, an
exemption from the `safeguarding_lead`, or a different team.

The subject (adult) or an active guardian (minor) may **withdraw** a pending
or approved registration (`*_withdraw` policies — the only update they can
make, and only to `withdrawn`). Withdrawal does not end an existing team
membership; that is an administrative act.

## 5. Audit

`registration.submitted` and `registration.decided` on `public.audit_log`,
detail `{person_id, season_id, team_id, status}`.
