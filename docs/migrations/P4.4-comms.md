# P4.4 — comms preferences, suppression, the one outbound API

`supabase/migrations/20260823190000_comms.sql` · Linear TH1-31 ·
Edge Function `comms-dispatch`

- `comms_preferences(person, channel, enabled)`: absence = enabled, except
  **SMS is opt-in**. Self/guardian-managed (`can_act_for`); admins read.
- `comms_suppressions(channel, address, reason)`: hard block (bounce,
  complaint, legal) that beats every preference and every category; admin-only;
  lower-cased by CHECK.
- `outbound_messages`: **the** log. `enqueue_message(channel, category,
  person?, address?, subject?, body?, template?, entity?, entity_id?)` is the
  only way in (service_role / club_admin): resolves the address from `people`,
  then suppression → preference (skipped for `transactional`) → `comms.dry_run`
  site setting → inserts the row as queued / suppressed / skipped_preference /
  dry_run / failed(no_address) with the decision recorded.
  `mark_message_sent` / `mark_message_failed` / `queued_messages` for the
  dispatcher (Resend for email, Twilio for SMS, Expo for push).
- The web app's existing Resend path calls `enqueue_message` first and marks
  the row; P4.2 arrears, P4.3 nudges and P5.5 push all go through it.

Tests: `supabase/tests/comms.test.sql` — 33 (defaults, resolution, opt-out
honoured for reminders/marketing not transactional, guardian manages child,
suppression beats transactional and matches case-insensitively, dry-run,
lifecycle, RLS).
