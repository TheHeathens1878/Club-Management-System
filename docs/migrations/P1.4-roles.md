# P1.4 — `public.person_roles`, `public.app_role`, `has_role()`

`supabase/migrations/20260822130000_roles.sql`

## What it does

Creates the role model `SAFEGUARDING.md` §1.3 describes, the helpers *"used by
**every** policy from here on"* (§4), and the one-directional bridge that keeps
the legacy `profiles.role` column and the new table in step while the imported
function-room app is still the thing writing roles.

It then re-expresses the P1.1–P1.3 policies that were left carrying
`TODO (P1.4)` markers. Those markers are the only reason this migration touches
another task's tables.

| Object | Purpose |
|---|---|
| `public.app_role` | Enum: `club_admin`, `safeguarding_lead`, `coach`, `staff`, `member`, `parent`, `hirer` — exactly the seven `SAFEGUARDING.md` §1.3 tabulates. A **separate** type from the baseline `public.user_role`, which is untouched. |
| `public.person_roles` | `person_id` → `people(id)` `on delete restrict`; `role`; `granted_at`; `granted_by` → `auth.users(id)` `on delete set null`; `revoked_at` (soft revoke); `notes`; `updated_at`. |
| `public.has_role(app_role)` | STABLE, SECURITY DEFINER, `search_path = public`. Does the **caller** hold this role right now? |
| `public.has_any_role(app_role[])` | The same question over a set — one index probe instead of a chain of ORs in a policy. |
| `public.person_has_role(uuid, app_role)` | The third-person form. Exists for SG-6's P2.1 triggers, which must ask about *somebody else*. |
| `public.is_club_admin()` / `public.is_safeguarding_lead()` | Thin wrappers, for policy readability. |
| `public.map_user_role_to_app_role(user_role)` + `..._strict()` | The legacy mapping, in one place, so the backfill and the sync trigger cannot drift. `_strict` raises on an unmapped value. |
| `public.backfill_person_roles()` | Returns `(roles_created)`. Idempotent. Suppresses the per-grant audit trigger while it runs. |
| `public.person_roles_audit()` | `after insert or update` → `role.granted` / `role.revoked` rows in `public.audit_log` (SG-7). |
| `public.profiles_sync_person_roles()` | `after insert or update of role on public.profiles` — the legacy bridge. **One-directional.** |
| `trg_person_roles_deny_hard_delete` / `trg_person_roles_deny_truncate` | P1.1's generic guards. Unlike `guardianships`, this table gets **both** — see below. |
| `trg_person_roles_updated` | The baseline `set_updated_at()`. |
| Indexes | `person_roles_active_idx` — unique on `(person_id, role)` **where `revoked_at is null`**; `person_roles_person_idx`; `person_roles_role_idx` (live rows). |
| RLS on `person_roles` | Four policies: self-read (live only), admin read (`club_admin` + `safeguarding_lead`), insert and update (`club_admin` only). No FOR DELETE policy, and none may be added. |
| Policy rewrite | `people_committee_*` → `people_admin_read` / `_insert` / `_update`; `guardianships_committee_*` → `guardianships_admin_read` / `_insert` / `_update` / `_delete`. |
| Grants | `revoke all` from the three API roles, then `select, insert, update` to `authenticated` and `service_role`; nothing to `anon`; `delete` and `truncate` revoked from all three and named explicitly. |

### What is deliberately *not* changed

`public.is_committee()`, `public.is_staff()` and `public.is_bar_manager()` are
untouched. They still read `profiles.role`, and the ~38 baseline policies that
call them behave exactly as they did before. The imported app's room bookings,
timesheets, holiday requests, bar rates and settings screens are unaffected in
every observable way. Policies migrate to `has_role()` **table by table**, as
each table's owning task reaches it; nothing is swept. The tests assert this
positively (three `prosrc ~ 'profiles'` checks), so a future sweep is a visible
test change rather than a silent one.

## The mapping

Applied by the backfill and, from now on, by the sync trigger. One shared
`IMMUTABLE` function owns it.

| `profiles.role` | `app_role` | Why |
|---|---|---|
| `super_user` | `club_admin` | `is_committee()` is true for it today; it is the highest privilege the old app has |
| `committee` | `club_admin` | §1.3: *"club_admin — Committee-level administrator"* |
| `bar_manager` | `staff` | §1.3 `staff` = *"Bar, clubhouse, ground staff"*. Managing the bar rota is not member-data authority |
| `bar` | `staff` | as above |
| `staff` | `staff` | identity |
| `member` | `member` | identity |

**Nobody is mapped to `safeguarding_lead`, `coach`, `parent` or `hirer`.**

* `safeguarding_lead` is Open Decision **D9**. §1.3 calls it *"the only role
  whose **purpose** is safeguarding"* and SG-3 makes it the sole writer of case
  notes. Deriving it from `profiles.role in ('committee','super_user')` would
  hand every committee member the Club Welfare Officer's readership of every
  concern in the club — including concerns about themselves, which SG-3's write
  model excludes in terms (*"A person named in a concern must not be able to
  read it, even if they are a `club_admin`"*). Adam assigns it by hand. Until he
  does, the role exists with no holders, and that is the correct failure mode:
  SG-3's reads return nothing rather than the wrong thing.
* `coach` cannot be derived — the old app has no notion of a team. It arrives
  with P2.1's `team_memberships`, gated by SG-6.
* `parent` is a label. §1.3: *"The role is a label; only the link (P1.3) carries
  authority over a specific child... Every rule below keys off the link, never
  the role."* Deriving it from `guardianships` would create a second, staler
  source of truth for a question `guardianships` already answers.
* `hirer` is *"deliberately isolated"* (§1.3), and the old app's hirers are not
  `profiles` rows at all.

The mapping is recorded in the backfill's own audit row, so the 39 prod grants
stay explained by one row a year from now.

## SG invariants

| Invariant | How this migration satisfies it |
|---|---|
| **SG-3** (restricted concerns) | The **helper half**. SG-3's whole write model is expressed as *"holders of `safeguarding_lead` or `club_admin`"*, and its enforcement note says each accessor function *"checks the caller's authority via the P1.4 `public.has_role()` helper"*. This migration makes that sentence executable. The concerns tables are P4.3. |
| **SG-6** (certification gating) | The **hook**. SG-6's *"Implemented by"*: *"P1.4 (`has_role`), P2.1 (`team_memberships` triggers, both directions...)"*. The composition-side guard must ask, of every existing membership on a team, whether that *other* person holds a child-facing role — which `has_role()` shaped like `is_committee()` cannot answer. Hence `person_has_role(uuid, app_role)`, which exists for that trigger and nothing else today. |
| **SG-7** (audit) | Role grants and revocations are logged by an `AFTER INSERT/UPDATE` trigger, following *"the existing `public.audit_log` conventions exactly"* and adding no parallel table. |
| **SG-2** (soft delete only) | Extended to this table by analogy, as P1.1 extended it to `public.people`. All four layers. Justified below. |
| **SG-0** | Untouched. Nothing here reads or derives age. |

## Decisions

### Soft revoke only — and why that is not inconsistent with P1.3

P1.3 declined `deny_hard_delete()` on `guardianships` and gave a reason. That
reason is absent here, so this table gets the guard.

* **SG-1.8 required the guardianship DELETE to stay reachable**, in terms: *"a
  flat reject makes a mistyped or genuinely-ended guardianship permanently
  unremovable, which is itself a data-protection problem."* There is no
  equivalent for a role grant. A role entered in error is corrected by revoking
  it — a first-class operation on this table — which leaves an honest record
  ("granted 09:14, revoked 09:15") rather than an unremovable falsehood. Nothing
  is stuck, so nothing is gained by allowing the delete.
* **The history is load-bearing in a way the row's absence would destroy.** SG-7
  requires safeguarding access to be attributable: *"any access to
  `safeguarding_concerns`"*, *"any read of `guardianships` outside a guardian's
  own links"*. Every one of those accesses is authorised by a row in **this**
  table (SG-3: readable *"only by holders of `safeguarding_lead` or
  `club_admin`"*). Delete the grant and the `audit_log` row it authorised becomes
  unexplainable: the log says a person read a concern, and the database says they
  never had the standing to. SG-6's compliance history
  (`expired_coach_appears_in_daily_compliance_report`) has the same dependency.
* **All four SG-2 layers, because §1.2 says only three things bind
  `service_role`**: the row-level `BEFORE DELETE` trigger, the statement-level
  `BEFORE TRUNCATE` trigger (a row-level delete trigger *never* fires on
  TRUNCATE), the revoked `DELETE`/`TRUNCATE` privileges with `service_role`
  named, and the absence of any FOR DELETE policy.

This extends SG-2 to a table its statement does not name. §6.2 permits a
strengthening without prior agreement and asks that it be recorded; it is, in
`DECISIONS.md`.

### The partial unique index

`(person_id, role) where revoked_at is null` — the same shape and reasoning as
P1.3's `guardianships_active_pair_idx`. A full `UNIQUE` plus a soft revoke would
mean a role, once revoked, could never be granted again, and the only way to
restore it would be to clear `revoked_at` on the old row, erasing the gap. The
gap is the history. Unlike P1.3's, this is not a deviation from anything: §4
specifies no uniqueness for this table at all.

The test asserts the exact `indexdef`, including the predicate.

### The `profiles` → `person_roles` sync is one-directional

The imported app still writes `profiles.role`, in five places
(`super-users/actions.ts:24`, `settings/actions.ts:124`, `:167`, `:225`,
`book/actions.ts:25`). Until P1.6 and Phase 4 move those screens onto
`person_roles`, a promotion made in the old UI must land in the new table or the
two models diverge on day one — and silently, which is the worst kind: a demoted
committee member would keep `club_admin` and with it every `people` and
`guardianships` read the rewrite below grants.

So `AFTER INSERT OR UPDATE OF role ON profiles` grants the newly mapped role and
revokes the previously mapped one. **Nothing propagates back**, and that is a
decision, not an omission:

1. It cannot be expressed. `profiles.role` is a single value; a person may hold
   several roles. Which of `{club_admin, coach, member}` would be written back?
2. `app_role` has values `user_role` has no equivalent for. Granting
   `safeguarding_lead` would have to pick a wrong legacy value or silently do
   nothing.
3. Writing back would make the old app's RLS respond to a grant made in the new
   model — precisely the sweeping change this migration says it is not making.

The reverse direction is **P1.6 / Phase 4**: the screens move onto
`person_roles`, `profiles.role` becomes derived-or-dropped, and this trigger is
deleted in the same task. Until then `profiles.role` is the source of truth for
the roles it can express, and `person_roles` for everything else.

Three properties are asserted rather than assumed:

* **`handle_new_user()` is deliberately not changed.** A signup is
  `auth.users` insert → `on_auth_user_created` → `handle_new_user()` →
  `insert into profiles`. An `AFTER INSERT` trigger on `profiles` fires for that
  insert like any other — it does not matter that another trigger issued it — so
  a new member gets their `member` grant without `handle_new_user()` knowing this
  table exists. Adding it there as well would be a second code path to keep in
  step for no gain. The test inserts an `auth.users` row and checks the grant
  appears (assertion 68).
* **The apps/web upsert shape still works.** PostgREST renders those upserts as
  `insert ... on conflict (id) do update`; the UPDATE branch fires the trigger's
  UPDATE arm (assertions 69–70).
* **No churn where the mapping does not change.** `bar` → `bar_manager` both map
  to `staff`, so the same grant row survives with its `granted_at`, `granted_by`
  and `notes` intact and no audit rows are written. Revoking and re-granting the
  same role would rewrite the history this table exists to keep (assertions
  66–67).

`granted_by` is left NULL by the trigger rather than filled from `auth.uid()`:
the grant was made by a machine translating a legacy column, and attributing it
to the person who clicked "make committee" in the old UI would be a small lie in
an audit trail. The SG-7 row still carries `auth.uid()` as the actor, which is
the honest record of who caused it.

### One summary audit row for the backfill, not 39

SG-7 wants role changes attributable, and the trigger writes a `role.granted`
row for every grant. For a backfill that is the wrong record: 39 rows attributed
to no actor, all at the same instant, all saying the same thing, burying the
grants a human actually made in the same table an auditor reads.

So the trigger checks a transaction-local GUC,
`app.person_roles_audit_suppressed`, which `backfill_person_roles()` sets while
it runs and clears afterwards, and the migration writes a single
`migration.backfill` / `person_roles` summary row carrying the counts **and the
mapping it applied**.

The GUC is set with `set_config(..., is_local => true)`, so it cannot outlive the
transaction even if the function raises. It is not a general-purpose escape
hatch: it is read in exactly one place, and the tests assert both halves — that
the backfill's six grants wrote no `role.granted` rows (76), that the GUC is
cleared on return (77), and that an ordinary grant immediately afterwards **is**
logged (80–84).

`detail` carries `{person_id, role}` and nothing else. SG-7: *"`detail` must
never contain the content it is logging access to"* — `notes` is not copied in,
because `audit_read` is `is_committee()` and therefore wider than this table's
own read policies. Assertion 83 attempts to find `notes` in `detail` and expects
not to.

### The policy rewrite: `people` write stays club_admin, `guardianships` write goes to both

The split is not the same on the two tables, and the asymmetry is deliberate.

**`public.people` — read for both admin roles, write for `club_admin` alone.**
§1.3 gives `club_admin` *"Full administrative access"*, and describes
`safeguarding_lead` as *"The only role whose **purpose** is safeguarding. Sole
read/write of concerns alongside `club_admin`; can export conversations."* Its
stated write remit is concerns. It needs to **read** `people` to do the job at
all — SG-6 asks it to be told which people are non-compliant, and SG-8 makes it
the only role that may set `legal_hold` (a column-scoped update that arrives with
P4.3, not a blanket one now). Editing a member's name, dob or address is
administration, so it stays with `club_admin`.

**`public.guardianships` — read *and* write for both admin roles.** Because SG-4
says so, in terms, and `SAFEGUARDING.md` §1 says the document outranks a task
description: *"RLS: a guardian may SELECT their own links and their children's
linked records; `club_admin` and `safeguarding_lead` may SELECT and write all;
nobody else sees the table."* SG-4 then makes that write access load-bearing
rather than incidental: *"Their write access is deliberate and is exactly why
SG-1.8 exists: an administrator correcting a family record must not be able to
silently strip the guardian out of a conversation the child is in."* Narrowing it
to `club_admin` would quietly re-specify SG-1.8's premise. Confirmed with Adam
2026-08-22.

**No `coach` policy on either table.** §1.3 gives `coach` no member-data access
by default, and the scoped read a coach actually needs ("the players on my team")
cannot be written until `team_memberships` exists (P2.1). Inventing a wider one
now and narrowing it later is the wrong order.

**No `staff` policy on either table**, unchanged from P1.1's refusal: *"No
inherent access to member or child data."*

`people_self_read` (P1.2), `people_guardian_read` (P1.3) and
`guardianships_guardian_read` are untouched: they key off `current_person_id()`
and a guardianship link, never a role.

#### Why the drop-and-recreate is additive in effect

Every profile whose `role` is `committee` or `super_user` — precisely the set
`is_committee()` returns true for — holds `club_admin` as of the backfill in this
same migration, and the sync trigger keeps that true for every future promotion
and demotion. No actor who could read `people` before the migration cannot read
it after. The suite asserts this as a regression (104–108), not as a hope.

The corollary is worth stating for the rehearsal: **the rewrite is only safe
because the backfill runs in the same transaction.** On an environment where the
backfill were skipped, committee members would lose their `people` read outright.

### `has_role(app_role)`, not `has_role(text)`

A typo'd role name in a policy becomes a migration-time type error instead of a
policy that silently never matches. `has_role('club_amin')` will not deploy.

`SAFEGUARDING.md` §4 lists the third-person form as `has_role(person_id, role)`;
it is named `person_has_role` instead, because `has_role(uuid, app_role)` and
`has_role(app_role)` are one implicit cast away from ambiguity in a policy, and
because a distinct name makes it obvious at the call site that the answer is
about somebody else.

### Why SECURITY DEFINER is load-bearing here, not stylistic

`person_roles` has RLS, and one of its own policies calls `is_club_admin()`. If
the helpers were SECURITY INVOKER the policy would re-enter the table's own RLS
to evaluate itself — the classic recursive-policy failure. As SECURITY DEFINER
they execute as the function owner (`postgres`), who owns the table and is
therefore not subject to its policies (RLS is enabled, never `FORCE`d), so the
lookup terminates. This is the same mechanism that lets the baseline's
`profiles_self_read` policy call `is_committee()`, which reads `profiles`.

It is also why `FORCE ROW LEVEL SECURITY` must not be added to this table: it
would break the helpers, and per §1.2 it would not bind `service_role` anyway.

### `anon` is revoked by name

Hosted Supabase's default privileges (`alter default privileges for role postgres
... grant execute on functions to anon, authenticated, service_role`) give every
new function an explicit grant to all three API roles, which
`revoke ... from public` does not touch. Found by the P1.1 preview-branch
rehearsal, where the local shadow DB had passed. All five helpers are revoked
from `public` **and** `anon` by name.

`has_role()` would answer FALSE for an unauthenticated caller and so leaks
nothing, but `person_has_role(uuid, app_role)` is a SECURITY DEFINER lookup on
somebody else's roles: granted to `anon` it is a probe — feed it a uuid and a
role and learn whether that person is the club's safeguarding lead. Both
assertions are in the suite (41, 42).

### A member does not see their own revoked roles

`person_roles_self_read` carries `revoked_at is null`. "You used to be a coach"
is a fact about an administrative decision, and if it was a safeguarding decision
the person should hear it from a human rather than discover it in a role list.
Admins see the full history, which is where the question belongs.

## Open gap: SG-7 reads

Unchanged from P1.3 and recorded again here: SG-7 requires an audit row for
*"any read of `guardianships` outside a guardian's own links"*, and the same
logic will apply to admin reads of `person_roles`. Postgres has no SELECT
trigger, so SG-7's own enforcement note makes those reads `SECURITY DEFINER`
accessor functions with no direct table grant behind them — a convention that
arrives with **P4.3** along with `public.write_audit()`. This migration closes
the *write* half of SG-7 for roles and leaves the read half open, deliberately.

are revoked first and every other profile already holds its mapped role, so `6`
is the answer on an empty database and on prod's alike.

## Rollback

Run as `postgres`, in one transaction, in this order.

```sql
-- 1. Restore the P1.1 / P1.3 policies this migration replaced.
drop policy if exists "people_admin_read"          on public.people;
drop policy if exists "people_admin_insert"        on public.people;
drop policy if exists "people_admin_update"        on public.people;
create policy "people_committee_read"   on public.people
  for select using (public.is_committee());
create policy "people_committee_insert" on public.people
  for insert with check (public.is_committee());
create policy "people_committee_update" on public.people
  for update using (public.is_committee()) with check (public.is_committee());

drop policy if exists "guardianships_admin_read"   on public.guardianships;
drop policy if exists "guardianships_admin_insert" on public.guardianships;
drop policy if exists "guardianships_admin_update" on public.guardianships;
drop policy if exists "guardianships_admin_delete" on public.guardianships;
create policy "guardianships_committee_read"   on public.guardianships
  for select using (public.is_committee());
create policy "guardianships_committee_insert" on public.guardianships
  for insert with check (public.is_committee());
create policy "guardianships_committee_update" on public.guardianships
  for update using (public.is_committee()) with check (public.is_committee());
create policy "guardianships_committee_delete" on public.guardianships
  for delete using (public.is_committee());

-- 2. Stop the legacy sync.
drop trigger if exists trg_profiles_sync_person_roles on public.profiles;

-- 3. Drop the table.
drop table if exists public.person_roles;

-- 4. Drop the functions, dependants first.
drop function if exists public.profiles_sync_person_roles();
drop function if exists public.person_roles_audit();
drop function if exists public.backfill_person_roles();
drop function if exists public.is_safeguarding_lead();
drop function if exists public.is_club_admin();
drop function if exists public.has_any_role(public.app_role[]);
drop function if exists public.has_role(public.app_role);
drop function if exists public.person_has_role(uuid, public.app_role);
drop function if exists public.map_user_role_to_app_role_strict(public.user_role);
drop function if exists public.map_user_role_to_app_role(public.user_role);
drop type if exists public.app_role;

-- 5. Record it.
insert into public.audit_log (actor_id, actor_email, action, entity, detail)
values (null, 'migration', 'migration.rollback', 'person_roles',
        jsonb_build_object('migration', '20260822130000_roles'));
```

Two notes. **Step 3 destroys the 39 backfilled grants**, which is correct for a
rollback of the migration that created them, and is the only circumstance in
which a `person_roles` row may be destroyed — `drop table` does not fire the
row-level delete trigger, which is why it is the one available route and why
nothing else in the schema can take it. **Step 1 must run before step 3**: the
`_admin_` policies reference `has_any_role()`, which the drop in step 4 would
otherwise refuse. The audit row written by the migration is **not** deleted:
audit rows are append-only (SG-2).

Order matters within step 4 too — `is_club_admin()` and `is_safeguarding_lead()`
call `has_role()`, and the backfill calls the mapping pair.
