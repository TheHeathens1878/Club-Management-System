Status 2026-08-23: **decided and built.** The Neon app hashes with `bcryptjs`
cost 12 (`$2a$12$…`, 61/61 users — MIGRATION_MAP §2/§5), so **Strategy A**
(import the hashes, no forced reset) applies to everyone. Adam's decisions

email matches are the same person.

## How it works

1. `select * from public.migrate_neon()` (P3.3, service_role) creates a
   `people` row per Neon user, or — 3a — stamps `legacy_neon_user_id` on the
   existing person when the email already belongs to an `auth.users` account
   (6 people in prod). Adults get **no DOB** (the Neon data has none) and no
   profile yet.
2. `node apps/web/scripts/neon-auth-import.mjs` (service role) reads
   `neon_auth_import_candidates()` — active users with a real email, a
   `$2a$12$` hash and no existing `auth.users` row — and calls
   `auth.admin.createUser({ email, password_hash, email_confirm: true,
   user_metadata: { full_name, person_id } })`. `--dry-run` lists instead.
3. `handle_new_user()` (extended in `20260824000000_neon_import.sql` §4)
   adopts the person when **both** `user_metadata.person_id` and the login
   email match it and the person is not a *known* minor. Metadata alone never
   adopts — `signUp()` lets anyone set metadata. Known minors still need the
   P1.7 `app_account` consent (unchanged).
4. The person now has a profile and an unknown DOB. SG-0 is not relaxed: they
   are a minor to every guard, so their team memberships sit in
   `neon_import_pending`. On first sign-in the web middleware (and the mobile
   `(app)` layout) send them to **`/complete-profile`**, whose only action is
   `complete_own_dob(date)` — allowed once, only for an imported person with
   NULL dob, audited as `people.dob.self_completed`. It then runs
   `apply_neon_pending(person)`: their memberships go live, with a 30-day
   `certification_exemptions` row where a child-facing role needs one (2a).
   A nightly cron (`neon-pending-nightly`) retries anything still queued.

Excluded from the import: the 3 "locked" child accounts
(`nologin-…@placeholder.invalid`, random hash) — people only; inactive
(never-approved) Neon users — people only, flagged in `notes`; Neon users
whose email is held by a *non-account* people row (a function-room hirer)
— people without email, flagged "merge by hand" (P1.2: never auto-link).
