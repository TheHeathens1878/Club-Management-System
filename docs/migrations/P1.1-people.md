# P1.1 — `public.people`

`supabase/migrations/20260822100000_people.sql`

## What it does

Creates the club's single identity table and the age machinery that
`SAFEGUARDING.md` SG-0 requires.

| Object | Purpose |
|---|---|
| `public.people` | One row per human the club knows — players (including minors), parents, coaches, staff, hirers. Names mandatory; everything else nullable. Soft delete via `deleted_at` / `deleted_by`. |
| `public.is_minor_dob(date)` | STABLE. `true` when the date is under 18 years before `current_date`, **or is NULL**. |
| `public.is_minor(uuid)` | STABLE, SECURITY DEFINER, `search_path = public`. Looks the person up and applies `is_minor_dob`; an unknown id returns `true`. |
| `public.people_dob_guard()` | `before insert or update of dob` — rejects a future DOB. The **single** dob trigger SAFEGUARDING §4 mandates; P2.1 and P5.2 extend this function rather than adding their own. |
| `public.deny_hard_delete()` | `before delete … for each row` — unconditional `raise exception`. Generic, so P4.3/P5.2 reuse it. |
| `public.deny_truncate()` | `before truncate … for each statement` — unconditional. A separate trigger because row-level DELETE triggers do not fire on TRUNCATE. |
| Indexes | `people_name_idx (last_name, first_name)`; `people_email_unique_live_idx` — unique on `lower(email)` where `email is not null and deleted_at is null`. |
| RLS | Enabled. Three policies, all `public.is_committee()`: read, insert, update. No `FOR DELETE` policy. |
| Grants | `revoke all` from `anon`, `authenticated`, `service_role`; then `select, insert, update` to `authenticated` and `service_role` only. `delete`/`truncate` revoked explicitly and re-stated. `execute` on both helpers to `authenticated`/`service_role`, revoked from `PUBLIC`. |

## SG invariants

| Invariant | How this migration satisfies it |
|---|---|
| **SG-0** (definition of minor) | Derived, never stored: two STABLE functions over `current_date`, no generated column and no cached boolean. NULL DOB ⇒ minor. Unknown `person_id` ⇒ minor. 18th birthday ⇒ adult. Proved by `people_is_minor.test.sql` (20 assertions, including that the functions really are `STABLE` — an `IMMUTABLE` marking would let a plan cache freeze a child at 17). |
| **SG-2** (soft delete only) — applied by analogy | `people` is not one of SG-2's four named tables, but §4's SG-8 row requires a departed member's record to be *pseudonymised*, never destroyed. All four SG-2 layers are therefore present: row-level delete guard, statement-level truncate guard, revoked `DELETE`/`TRUNCATE` (with `service_role` named — it holds `BYPASSRLS`, so the revoke and the triggers are the only controls that bind it), and no `FOR DELETE` policy. Proved by `people_rls.test.sql` as `authenticated`, as `service_role` **and** as the table owner. |
| **SG-8** (retention) | Groundwork only: `legal_hold boolean not null default false` and `pseudonymised_at timestamptz` exist per the §4 checklist. Nothing reads them; the retention job is P5.6 and ships disabled. |

## Decisions taken

**Email is `text`, not `citext`.** A partial unique index on `lower(email)`
delivers the same case-insensitivity without adding an extension. `citext`'s
comparison semantics interact awkwardly with non-C collations and it is not
installed on the project today; avoiding it keeps the extension list as the
baseline left it.

**Email is unique among live rows** — `unique (lower(email)) where email is not
null and deleted_at is null`. Accepted rather than rejected, because duplicate
person rows split a member's history, mis-address safeguarding correspondence,
and make P1.2's `profiles → people` backfill ambiguous (`auth.users.email` is
itself unique). The obvious objection is that families share an address: the
club rule this encodes is that **a minor's contact route is their guardian**, a
`guardianships` row in P1.3, not the parent's email copied onto the child's
record. A person with no email of their own leaves it NULL and the partial index
permits any number of those. Two consequences, both intended: soft-deleting a
person releases their address for re-use, and the Phase 3 Neon import must
dedupe or NULL colliding emails rather than loading them as-is.

**Address is a single `address jsonb` object**, not five columns. The club never
filters, joins or aggregates on an address component — it is correspondence
data, printed or posted as a block. UK addresses are irregular (sub-buildings,
no street name, BFPO), and the fields actually wanted are not settled until the
P2.2 registration form is designed; jsonb defers that without a migration per
field. A `check (jsonb_typeof(address) = 'object')` stops an array or a bare
string getting in. Recommended keys: `line1`, `line2`, `town`, `county`,
`postcode`, `country`. If a component ever needs indexing, an expression index
on `(address ->> 'postcode')` costs nothing to add.

**29 February: majority is attained on 1 March in a non-leap year.** The
predicate is `dob > current_date - interval '18 years'`. Postgres clamps an
interval subtraction landing on a non-existent date to the last day of the
month, so someone born 29 Feb 2008 is still a minor on 28 Feb 2026 and an adult
from 1 March 2026. This is the fail-closed direction — an extra day of
protection, never a day short — and matches the ordinary English-law reading of
a leap-day anniversary. `age()` gives the same answer; the interval form was
chosen because it is a single sargable comparison against the column, which
`age(current_date, dob) < interval '18 years'` is not.

**NULL DOB ⇒ minor; unknown `person_id` ⇒ minor.** SG-0 / Open Decision D1,
verbatim. `is_minor(uuid)` coalesces a missing row to `true`, so a typo'd or
deleted id can never come back as "not a minor". A **soft-deleted** person is
still evaluated on their DOB: `deleted_at` says nothing about someone's age.

**"DOB not in the future" is a trigger, not a `CHECK`.** `current_date` is
STABLE, and Postgres refuses non-immutable functions in check constraints. The
lower bound (`>= 1900-01-01`) *is* a `CHECK`, because it is a constant. The two
therefore fail with different SQLSTATEs — `P0001` and `23514` — and the tests
assert exactly that.

**One trigger on `people.dob`.** SAFEGUARDING §4 is explicit: "One `people`
`UPDATE OF dob` trigger, carrying both SG-1.2 and SG-6 tier 1(c) — not two
triggers on the same column." `people_dob_guard()` is that trigger, created now
with only the range validation in it and a marked extension point. **P2.1 and
P5.2 must extend this function, not add another trigger.**

**Generic guard function names.** The task asked for
`deny_hard_delete_people()`; the migration creates `public.deny_hard_delete()`
and `public.deny_truncate()` instead — the exact names SAFEGUARDING §3/§4 use —
so that P4.3 (`safeguarding_concerns`) and P5.2 (`messages`,
`conversation_participants`, `audit_log`) attach the same two functions rather
than re-implementing the rule four times. The *triggers* are per-table
(`trg_people_deny_hard_delete`, `trg_people_deny_truncate`), and the exception
message names the table via `tg_table_name`.

**No `people_staff_read` policy — a deliberate departure from the task
description.** The task asked for "staff = read" via `public.is_staff()`, which
resolves TRUE for `bar`, `bar_manager` and `staff` as well as committee.
SAFEGUARDING §1.3 says of `staff` ("bar, clubhouse, ground staff"): *"No
inherent access to member or child data."* A blanket staff read here is every
child's date of birth, home address and notes, readable by whoever is behind the
bar on a Saturday. SAFEGUARDING §1 states that where it and a task description
disagree, the document wins and the task is re-specified — so the policy was not
written. Nothing is lost today: the table is empty until P1.2's backfill.
**This needs Adam's decision in P1.4**, where `has_role()` allows the reads that
are actually appropriate (a coach seeing the players on their own team, a
`safeguarding_lead` seeing all, a `hirer` seeing nothing).

**`anon` gets no execute on the helpers.** `is_minor()` is SECURITY DEFINER over
`public.people`; granting it to `anon` would hand an unauthenticated caller an
oracle — probe a uuid, and a `false` answer proves both that the person exists
and that they are an adult. `is_minor_dob()` is harmless in itself but is
revoked alongside it for symmetry: there is no anonymous surface that needs it.

**Self-read is a marked TODO, not an invented column.** A person must be able to
read their own row, but the linkage (`profiles.person_id`) does not exist until
P1.2. The policy is written out in a comment block in §7 of the migration, ready
to paste, with the note that a future *self-update* policy must not permit
editing `dob` — SG-0 is load-bearing and a DOB change is an administrative act.

## Tests

`supabase/tests/` — 3 files, **70 assertions**, all passing.

| File | Assertions | Covers |
|---|---|---|
| `people_is_minor.test.sql` | 20 | NULL DOB, the 18th-birthday boundary in both directions, far past, born today, both 29-Feb directions (with dobs computed relative to `current_date` so they do not rot) plus the fixed-date pair that pins the convention, `is_minor` over real rows including a soft-deleted one, unknown and NULL `person_id`, and the `STABLE` / `SECURITY DEFINER` / `search_path` properties SG-0 depends on. |
| `people_rls.test.sql` | 31 | Exact policy set (`policies_are`), RLS enabled, no `FOR DELETE` policy, exact table privileges per API role (`table_privs_are`) plus explicit DELETE/TRUNCATE assertions, function-execute privileges, anon denied, member and staff read nothing, staff insert denied, staff update silently no-ops, committee read/insert/update, and delete + truncate refused as `authenticated`, as `service_role` and as the **table owner** (the owner run is the one that proves the trigger rather than the grant). |
| `people_constraints.test.sql` | 19 | Blank names, future DOB on insert *and* update, pre-1900 DOB, the 1900-01-01 and today boundaries, malformed and whitespace-padded emails, case-insensitive duplicate rejection, unlimited NULL emails, email re-use after soft delete, address must be an object, and the `updated_at` trigger. |

pgTAP itself is installed by `supabase/seed.sql` (into `extensions`), not by a
migration — the test framework has no business existing on the hosted project,
and `seed.sql` is the only file that runs locally and in CI but never in a
`db push`.


Two footnotes on those commands:

* `db lint` is scoped to `--schema public`. Unscoped it also lints `extensions`,
  where pgTAP's own function bodies produce eight plpgsql_check errors (deferred
  temp-table references, version-guarded catalog columns). We lint our schema,
  not a third-party extension's. `.github/workflows/ci.yml` was updated to match
  and to run `supabase test db`.
* `gen types --local` fails with `password authentication failed for user
  "postgres"` unless `SUPABASE_DB_PASSWORD=postgres` is set, because the project
  is linked and the CLI reaches for the linked project's password. The committed
  file preserves the four-line hand-written header and the `__InternalSupabase`
  / `PostgrestVersion` block that the `--linked` generator emits, so the diff is
  purely additive.

## Rollback

```sql
drop table if exists public.people cascade;
drop function if exists public.is_minor(uuid);
drop function if exists public.is_minor_dob(date);
drop function if exists public.people_dob_guard();
drop function if exists public.deny_truncate();
drop function if exists public.deny_hard_delete();
```

Dropping the table removes its triggers, indexes and policies with it; the two
guard functions come last because the triggers reference them. No data is
touched — the table is new and empty, there is no backfill and nothing else in
the schema references it yet.
